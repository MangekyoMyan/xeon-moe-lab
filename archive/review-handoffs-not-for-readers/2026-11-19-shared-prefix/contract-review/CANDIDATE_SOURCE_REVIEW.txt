Independent review of the 169a three-node scheduler candidate, 2026-11-19

I reviewed the 288-line proposal in astra62/prefix-candidate/shared_prefix.inc (SHA256 49ffb58d1af1dcdca33b9536dce5c50eed6147b53ba1954bca31b9b76ae419a4) and shared-prefix.patch (SHA256 30ef5083614f2a3b9cc2e4418639b877d355c09df91a3b9121489511cc898f43), then inspected the parent's changes in prefix-engine. This is a source review for the isolated single-caller model trial.

Teardown correction

The original helper's line 42 dereferenced the stored GPU backend handle during scheduler destruction. The owning vector of ggml_backend_ptr lives at deepseek41-bringup-20261101/source/src/llama-context.h line 396, after the scheduler member at line 367. C++ destroys the vector first. Its deleter calls ggml_backend_free, and CUDA 45f6's ggml_backend_cuda_free deletes the backend and its context (ggml-cuda.cu lines 2724–2729). Calling ggml_backend_synchronize with that handle from prefix169_free could therefore use freed memory even after a successful quality run.

The parent removed that call in prefix-engine/shared_prefix.inc. The pinned llama_context destructor calls synchronize() while both members live, before the destructor body ends (llama-context.cpp lines 586–608). That calls ggml_backend_sched_synchronize at line 893, which synchronizes each backend (frozen gpu-stream-20261103/ggml-backend.cpp lines 2405–2409). The private CUDA buffer's own destructor directly frees its owned CUDA allocation without the stored backend handle (CUDA lines 780–788). The scheduler can therefore free the independent scratch buffer and context after the pinned caller has synchronized. Non-context callers must quiesce the scheduler before destroying it. The pending guard still drains failed submissions while the handle is live. Inspected the correction and exact two-backend guard in the parent copy.

Dispatch and cache checks

1. New scheduling is selected once for a full graph allocation. The helper requires 37 matched ordered CPU/GPU pairs. All four CPU node outputs and their sources are host buffers. The same normalized activation used by the first two shared projections is traced to the CPU input copy by identity and zero-offset view. The code also identifies copied IDs, the CPU-down H2D copy, matched shared weights and original final ADD operands. The parent additionally requires CUDA0/CPU in order, exactly two backends and a NULL CPU async-copy entry. One pipeline copy and absence of an eval callback are checked. An unsuccessful plan match leaves the original graph available.

2. The early graph is the original contiguous gate/up/clamp view. Three RAII guards bind distinct backend-allocated F32 scratch slots and restore the original data and buffer fields before the CPU call. The CUDA remainder owns its node pointer array, omits exactly those three nodes and keeps the original hash/use counts. Within its dispatch, the original clamp descriptor points to the scratch result. Identity, all source pointers, clamp, final ADD source order and the adjacency of shared down and ADD remain intact. F32 CUDA kernel arguments capture the device values before return. The earlier source review gives the MMVQ and SwiGLU source lines. Actual CUDA capture and kernel behavior still require quality/count checks for the candidate.

3. Each scheduler re-split creates a fresh UID for all split views before new allocations. The plan compares split[0].graph.uid. It creates distinct stable UIDs for early and filtered views and retains different natural per-layer first-tensor keys. CUDA caches by first tensor and uses equal nonzero UIDs to skip property comparison (CUDA lines 2882–2926). The candidate checks the saved data and buffer of the original three outputs, down, ADD, norm and three weights before each matched dispatch. The fixed graph generation owns their immutable shapes, op parameters and remaining sources. An altered graph generation rebuilds those checks and new view UIDs. Running the original GPU split after a prelaunch mismatch uses the original full graph's UID.

4. If the check fails before early submission, CPU runs normally and the following GPU uses its original complete graph. After early work is submitted, the pending guard survives errors from the early GPU, CPU, binding check or filtered GPU. Model-level error return destroys the guard and synchronizes the existing GPU backend. RAII restores all tensor descriptors before that outer drain. A successful filtered submission clears pending. Normal same-stream execution, the following input-copy fences and the context's existing final sync order scratch reuse and teardown. A dedicated fixed process, one caller, a single copy, exact providers and the graph optimizer setting checked at scheduler creation are material to this conclusion.

5. The stage counters permit verification of 37 matching early submissions, 37 corresponding filtered submissions and zero fault drains for each T=1, with ordinary multi-token prefill. The experiment needs both complete 65-row F32 comparisons and a successful child exit through resource destruction. The parent's independent original-provider trace verified 296 eligible historical-order intervals over eight calls, with a median 1.611742 ms/token of prefix device work. This establishes the size of the measured interval. The candidate's whole-token change is a separate result.

Build observation

The first candidate compile log reported invalid use of extern at the C-exported stats prototype and definition. GGML_API already adds extern in the shared GCC configuration (ggml/include/ggml.h line 184). The parent replaced it with an explicit default-visibility attribute on the Linux C export. I checked the final helper declarations and build receipt. The final helper SHA256 is 5e9a2131b6450b610335725043662fa7f68a432a91f934f7b4e8a3a056fe4009. The control object and DSO were byte-identical to frozen, and the corrected candidate compiled and linked with DSO SHA256 c586449d1f06819062656502f192d2e1ec2aa3d79869b07d8406fe1394251b7e. The parent owns runtime correctness validation and timing. I ran no engine code or tests in this review.
