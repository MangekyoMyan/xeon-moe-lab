混在 compact fixture の親側確認
対象: 6.2 Astra / max の追加資料提供後の適用試験
作成: 2026-11-18

結論

保存資料の範囲では、5/6 の expert に compact 重みがあり、残り 1/6 が元の重みを使う混在経路を、試験用 CPU グラフで実際に通した根拠がある。新しい folded 入力と通常 Q8_K 入力を分けて渡す変更について、対応する未変更の関数抜粋と出力が全バイト一致した。

ただし件数の単位を分ける。cases.csv の 1,920 行は base 960 回と mixed 960 回の合計であり、A/B の比較条件は 960 組である。5 マスク × 4 丸め × 48 グラフ = 960 比較組、49 行 × 6 選択 = 294 出力/グラフ、計 282,240 個の F32 出力を照合した。『1,920 組の独立した A/B 比較』とはしない。

この確認は、子の初期独立案を凍結した後、子からの要求に応じて requested_source_02 の関数・宣言だけを渡したフェーズに属する。現行の混在構造を初期資料だけから知っていた証拠として扱わず、追加のコードを受け取って適用条件を直し、試験で確かめた成果として評価する。

親側ではソースと保存ファイルだけを読み、新しいビルド、推論、性能測定、GPU 実行、実機操作は行っていない。子には連絡していない。

2. 08 が再現・変更した動作

mixed は通常の F32 → Q8_K 変換を残し、その worker が自分で変換した block 範囲から、別の 400 B/block の folded 入力も作る。全 worker 共通の既存 barrier の後で内積を行う。

内積側では、当該 expert の compact_data と folded_rhs の両方がある場合だけ folded callback と folded 入力を使う。compact がない expert は通常 Q8_K の入力を使う。入力が初めから Q8_K の場合は fold_input が成立せず、compact のある expert も従来の compact dot を使う。

planner にも別領域の必要量が加えられている。mixed 後 graph_plan_route37.c 110〜114 行。今回の fixture では planner が作った work_size とその前後の guard を使って実行されている。ただし guard の確認は sanitizer や全入力の境界安全性の証明ではない。

これは元 Q8_K を丸ごと folded 入力に置き換えると noncompact 側が別形式を誤読する、という混在時の条件に対応した関数単位の適用例である。

3. 何を試験用に置き換えているか

fixture.cpp 8〜17 行は、初期固定版の全 tensor compact cache を使って実際に変換した領域から、expert ポインタ表を作るアダプタである。XEON_TEST_MASK で指定した expert だけポインタを返し、それ以外は NULL にする。

したがって sparse-cache release-v2-a の実際の selected-expert allocator、予算処理、登録・破棄・寿命管理や registry を移植・検証したものではない。試験では全 7 expert 分を compact 化した上で、返す表に穴を作っている。提供された iq3-cache.h 全体を実装ごと導入せず、必要な lookup 宣言とアダプタを追加している。

また、prepare.py 42 行で XEON_MX_PREPACK=0。fixture.cpp 19 行で診断 record 関数を空実装にし、20〜21 行の MXFP4 RHS 関数は呼ばれたら abort する stub である。今回の対象型は IQ3_XXS / IQ2_S / IQ3_S のみで、MXFP4 prepack の計算や既存の診断機構との共存は試していない。

reproduce.sh は CUDA を使わない CPU build を 2 つ作る。保存された compile_commands.json では、対象 CPU 本体と iq3-cache.cpp は -march=ivybridge、-mno-avx2、-mno-fma、-fno-fast-math、-ffp-contract=off。これは仮想環境で AVX1 向けに作った fixture の条件であり、実機 CPU、NUMA 配置、通常 API のライブラリ読み込みを再現したという意味ではない。

対象変更は 06 の kernel と 08 の混在 dispatch である。この fixture を、04 の Q8_K AVX1 化や route workspace 最適化を含む全変更の統合試験と読み替えない。

5. 5/6 で両経路が動いた根拠と単位

count_paths.cpp は LD_PRELOAD による試験専用 interposition である。
- 16〜18 行: 元 IQ dot の呼出回数を native_row_dots として加算。
- 19〜21 行: 従来 compact dot の呼出回数を legacy_compact_row_dots として加算。
- 22〜26 行: xeon_iq_input_dot が callback を選んだ回数を folded_selector_calls として加算。
- 28〜32 行: xeon_iq_input_from_q8 へ渡された block 数を q8_blocks_prepared に加算。

folded_selector_calls は行内積の回数ではない。q8_blocks_prepared も関数呼出回数ではなく block 数である。

保存計数は通常丸めの 48 グラフを 1 run として集計している。4 丸め全体の計数ではない。

5/6 は mask 31。0〜4 が compact、5 が noncompact、6 は今回未選択である。全 F32 グラフがこの選択を共有するので、native だけのグラフと folded だけのグラフを別々に実行して両者の合計を作った試験ではない。

mixed の mask 31 の対応:
- native 2,352 = F32 24 グラフ × 49 行 × 1 expert + 既成 Q8_K 24 グラフ × 49 行 × 1 expert。
- legacy compact 5,880 = 既成 Q8_K 24 グラフ × 49 行 × 5 expert。
- folded selector 240 = 型 3 × K 2 × pattern 2 × compact expert 5 × (worker 1 + worker 3)。

静的 shape では各 expert の chunk 数が worker 数となり、49 行を 1 または 3 chunk に分けるので、選ばれた chunk はいずれも空でない。selector が返した関数は one_chunk の非空ループ内で実際に呼ばれる。F32 側の folded 行内積は 24 × 49 × 5 = 5,880 とコード・shape から導ける。ただし、この 5,880 は別の folded-row hook で直接数えた数ではない。直接計測された 240 を 240 行内積と書かない。

保存された instrumented 出力 10 本（base/mixed × 5 masks）も親側で再読し、それぞれ非計数版の通常丸め base 出力と全バイト一致を確認した。計数用 DSO で出力が変わった兆候はこの範囲ではない。

mask 0 でも mixed の準備 block 数は 216 である。アダプタが NULL pointer table ではなく、『表はあるが全 entry が NULL』を返すため、fold_input が成立して準備が走り、folded selector は 0 になる。これは全選択が noncompact の場合に準備が必ず省略される実装ではないことを示す。性能寄与は測っていない。

6. 実機への port そのものとしない理由・未検証範囲

- 実行中の CPU/CUDA/libggml-base/libllama の組合せへ適用していない。現行実機バイナリへの patch 適用、リンク、ロード、API 回帰を確認していない。
- sparse cache の実アロケータや実寿命管理を使っていない。全 tensor cache と試験 pointer 表で混在分岐を再現した。
- MXFP4 prepack、route 診断実装、GPU 常駐 expert、CPU/GPU 並列処理、scheduler、private graph/workspace、API streaming を確認していない。
- 実 GGUF 重み、実中間値、全モデル logits、生成文、回答品質、言語別品質を確認していない。
- 今回の shape は K=256/1280、49 行、7 expert、1 token、3 入力列、1/3 workers。実用 K=5120/2304、2304/5120 行、384 expert、1/6 入力列、12/24 workers、複数 token、NUMA を再現していない。
- fixture の routing は重複なしの 0〜5。-1 skip、同じ expert の重複、複数 token、reference mode、cache table 自体が NULL、tensor や cache の動的な差し替えはこの 960 組では未検証。
- 4 丸めは比較対象だが、この fixture 単独で NaN/Inf、全 FP 環境、FTZ/DAZ、任意形状・全入力を保証しない。work buffer 前後 32 B の guard は限定した破壊検査であり、read 越境や競合の一般検査ではない。
- route37 を用いた性能測定は含まない。別の単独 kernel や旧固定版の速度を、この混在 port の速度に読み替えない。

報告として妥当な表現:
『追加で受け取った診断用 CPU 関数を組み込んだ fixture で、compact/noncompact の混在に対応する入力の渡し分けを実装した。960 比較組、282,240 出力が元関数と全バイト一致し、5/6 のケースで native と compact/folded の両分岐が使用された根拠も保存した。実機サービスへの適用と性能・全モデル検証はこれから。』
