結論

最終5個の CPU DSO の visible feature 組合せは期待通りで、先に見つかった iqsafe / combosafe の同一バイナリ問題はこの snapshot にはない。
新しい source/flags の食違いを示す具体的な懸念も、今回の確認範囲では見つからなかった。
base DSO は hash が異なるが、今回重要な quantize_row_q8_K_ref は命令列と参照する定数の値が全5版で一致した。hash差を算術差と解釈する必要はない。

iqsafe / combosafe は folded_dot 3個に has_min の読取り・補正分岐があり、修正前 folded の存在だけを合格にしていない。

親から最終 route2/combosafe の独立 graph 参照再検証、最終 iqsafe の prepared bytes と dot 出力比較の成功報告があった。本書の担当は、その既に十分な実行検証を繰り返していない。これら数値は親の実行 receipt に帰属させる。

2. base DSO の hash 差を絞って確認

全5 base の quantize_row_q8_K_ref を抽出した。baselineとの listing 差は5箇所の RIP-relative 定数の参照アドレスだけだった。
そこで各参照先の4-byte内容を ELF の section offset から読み出し、命令列へ埋め込んで比較した。全5版で命令列・参照値が一致した。

確認した定数 bytes (little endian):
  ff ff ff 7f
  00 00 fe c2
  ff ff 7f 00
  00 00 40 4b
  00 00 80 3f

これは「RIPのoffsetを消したら同じだった」だけではなく、参照先の定数値も照合した結果である。
各 base には異なる source directory を含む文字列が埋め込まれていた。source path長による rodata 配置差と整合する。ただし ELF 全 bytes の差をすべて source path に帰属したという意味ではない。
base の全関数を意味的に比較したものでもない。

3. source と compile options

4つの isolated source の下記ファイルは、いずれも初期 vendor/llama.cpp のファイル hash と一致した。
  ggml/src/ggml-quants.c
  ggml/src/ggml-quants.h
  ggml/src/ggml-common.h

4つの build-isolated-* の ggml-base / ggml-cpu の C/C++ flags と defines は同じ。
主な設定は -march=ivybridge -mtune=ivybridge -mno-avx2 -mno-fma -O3、OpenMP有効。
CPU側の ggml-cpu.c / ggml-cpu.cpp / iq3-cache.cpp の個別 options は -fno-fast-math;-ffp-contract=off で、4 build間で一致した。
新しい base全objectにこの個別optionsが付いているとは扱わない。

現在の古い work/build/ の flags.make は後の ASAN 用設定へ変わっていた。これを最初の baseline DSO の build flags と取り違えない。親が保存した baseline DSO は最初の hash と同じで、最終5 DSOの symbol には ASAN参照は見つからなかった。

新しい4 buildの source home は各 isolated-* に分離され、flags.make も別 directory にある。既存共有 build directory の incremental状態を最終結果の根拠にはしていない。
