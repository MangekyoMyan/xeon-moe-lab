# 会話の保存・分岐・復帰を実機のCLIで検証

共通地点からAに箱番号 `731`、Bに `284` を登録した。Bをさらに407トークン進めてからAに戻すと、**履歴の再計算は0トークンで、Aは `731` と回答した**。エンジンと管理プロセスを再起動してBに戻しても `284` が返った。サーバー上の二つの端末で使える。[起動と日常の操作例](../../../current/experiments/state-branches/README.md)

## 同じ長さの枝と保存予算

Pを処理した時点で `mark` し、そこからAとBを作った。Pは77トークン（3,432,132バイト）。AとBは**ともに114トークン・5,069,896バイト**で、実際のID列・画像SHA・保存点IDは異なる。親を参照するだけのforkでは画像バイト数が増えず、別の枝をreleaseした後も親の画像を読めた。母体のDeepSeekはraw窓が128であり、Bの追加はその窓を超えている。[枝ごとの記録](evidence/basic.json)・[CLIの応答と時刻](runs/basic-1/observations.jsonl)

画像予算を合成試験の3,433,156バイトまで縮めると、保持画像は102,523,124→3,432,132バイトとなり、pinした親が残った。適合する祖先画像もなくなった255トークンの枝は、先頭から255トークンを再入力して復帰できた。この予算は重複を除いた完全native画像に適用する。SQLiteの容量と確定前の作業ファイルを分けて扱う。[予算変更と再入力](evidence/budget.json)

## 入力・切替・障害回復

| 実機で作った状況 | 観測した動作 |
|---|---|
| 同じticketで二つのcheckoutを同時送信 | 1件成功、1件は古い世代として拒否。遅延したmarkも拒否 |
| 114トークンの画像を欠損させる | 77トークンの親を復元し、37トークンを再入力。作り直した保存画像のトークン列を確認 |
| 同じサイズの画像の内容を変える | SHAの不一致を検出し、77＋37トークンで復帰 |
| 移動先のnative復元でエラー | 元の枝の確定画像を復元。論理headとactiveは元の枝を指す |
| 移動先・元の枝のnative復元が両方失敗 | スロットをinvalidにして次の生成を拒否。`recover` で元のheadを再構築 |
| native復元成功直後、activeのcommit前に管理プロセスを強制終了 | 同じバックエンド上では切替・回復を保留。新しいバックエンド世代で、以前の論理headに復帰 |
| 保存領域に異なるcodecのbindingを指定 | 互換性不一致を返し、復元前に停止 |

nativeエラーは試験専用アダプターが存在しない合成画像名を指定して実際のサーバーから返させた。管理プロセスの中断試験では、nativeの成功応答を受け取った直後にその試験プロセスのみ終了させた。[障害試験の実装](fault_manager.py)・[失敗時を含む応答](runs/deep-1/observations.jsonl)

実機のUTF-8例では `🪿` を1文字だけ返すよう指示し、`🪿` を受信した。生成は終了トークンを含む4 IDで、個別のストリームイベントに載ったのは2 ID。独立HTTPアダプターが返す全サンプル列を使い、未入力の末尾ID `1` と、native画像内の処理済み344トークンを分けて照合した。[最終応答の変更](../../../current/experiments/state-branches/native-stream.patch)・[実機の生成記録](evidence/final-cost.json)

## 普段のターンと切替の費用

計装なし、サーバー内のUnixソケットで測定した。通常ターンは255を再利用して33トークンを追加し、各経路4回を順序を入れ替えて比較した。初回本文までの計時にはテンプレート適用を含み、管理CLIでは世代の取得も含む。終了点はクライアントによる最初の非空本文の受信。CLIのコマンド解釈とPython起動時間はこの比較の外側にある。通常ターンの追加画像は全件0バイトで、CLIは完了時にトークンログと論理headを確定した。

| 中央値 | 手動native | 管理CLI | 差（CLI－native） |
|---|---:|---:|---:|
| 普通のターンの初回本文、各4回 | 1.929秒 | 1.981秒 | +52 ms |
| 普通のターンの完了、各4回 | 2.050秒 | 2.211秒 | +162 ms |
| 未保存の枝を保存して他の枝へ切替、各2回 | 0.019秒 | 0.667秒 | +647 ms |
| 上記の切替開始から次の初回本文、各2回 | 1.724秒 | 2.466秒 | +742 ms |

切替時は両経路とも285トークン・6,193,740バイトの未保存状態を保存し、同じ移動先画像を復元した。続くターンは293再利用＋29新規で同じ `731` が出た。どちらも同じ1 GiB予算内で、手動側はnativeの保存・復元APIを直接呼んだ。CLI側の時間には検証・画像の確定・SQLiteの永続化・世代照合を含む。各費用の内訳はこの試験からは決まらない。

初回本文の各回は、手動が1918.1 / 1886.8 / 1941.7 / 1939.1 ms、CLIが1951.4 / 1959.4 / 2034.1 / 2002.6 ms。切替操作の各回は、手動が19.3 / 19.0 ms、CLIが639.0 / 694.2 ms。回数が少なく、このホストのこの長さでの測定である。[すべての時刻・条件](evidence/final-cost.json)

## 再現と実機の状態

公開ZIPを展開して `python3 -B replay.py` を実行すると、標準ライブラリでファイルのSHA、native画像内のトークン、全語彙行、操作・性能集計、CLIの回帰試験を確認できる。ZIPに含む保存画像はこの試験で作った架空の会話だけである。[再現用Release](https://github.com/MangekyoMyan/xeon-moe-lab/releases/tag/state-branches-20261128)

利用者に案内する `branch open` 自体も空の試験用カタログから起動し、別プロセスのCLIで会話・保存・分岐・切替を行い、Ctrl+C相当で元のAPIへ戻した。通常APIは24/24・64/64、GPU150 W、ECC有効、ファン上限70%で復帰した。6回の独立エンジンが正常終了し、最終の通常APIの設定・ライブラリは開始前と一致した。[端末からの確認](evidence/entry.json)・[復帰と監視の記録](SERVICE_RESULT.json)
