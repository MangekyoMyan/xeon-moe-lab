要点

保存された raw と source は、今回の報告の主要な数値・対象範囲と一致する。
元の ubatch1024、同じ時相の従来 guard のまま、32 expert の容量 fixture が
実際に初期化され、その bank を保持した状態で主モデルの short64 / long1024
試験が完了している。以前の post-vision free を pre-vision guard と比較して
いた容量不足推定は、今回の実測によって修正するのが適切である。

ただし、この成功は「32 expert の容量 fixture を確保できた」という結果。
主モデルはその bank を演算に使っていない。first5 から選んだ 35 expert / 23層
案は別の配置で、未 allocation・未 admission・未統合である。並列性能や回答品質
の採用判定へ読み替える根拠は、この package にはない。

3. 容量 fixture の実測

fixture は事前固定の layers 0,4,23,24 × expert IDs 0..7 =32 experts。
IQ2_S / IQ3_XXS / IQ3_S / MXFP4 の組み合わせを含む。native triplet byte は
source の block size と tensor shapeから独立に算出し、inventory・planと一致。
  IQ2_S   256 elements / 82 bytes
  IQ3_XXS 256 elements / 98 bytes
  IQ3_S   256 elements / 110 bytes
  MXFP4    32 elements / 17 bytes

native payload:      480706560 B =458.4375 MiB
bank buffer request: 480707328 B =458.438232421875 MiB
差:                         768 B

実際のログから guard を独立に再評価:
  Gpre free 3814981632 B > payload 480706560 B + margin 3221225472 B
  headroom =113049600 B =107.8125 MiB
  Gpost free 3288596480 B > margin 2684354560 B
  headroom =604241920 B =576.25 MiB

Gpre / Gpost はいずれも vision 前。Gpost は private graph / pool / reachable H
warmup の後であり、M1 / M2 の値を guard に代入したのではない。

CUDA API free MiB:
  phase                              bankなし       32expert保持
  M0 context reserve後/vision前       3638.25         3638.25
  Gpost private bank初期化後          該当なし       3136.25
  M1 vision dummy shape reserve後    2612.25         2110.25
  M2 text64 warmup後                 2122.25         1654.25
  M3 long1024+4T1/export後            2102.25         1630.25

初期の free 差502 MiBから bank bufferを引くと43.561767578125 MiB。
これは今回のその他初期化費の合計差であり、個別 allocator/graph/pool の内訳でも、
別配置へ使える普遍的な固定 overhead でもない。

CUDA と NVML は順次問い合わせ。CUDA total=32494.125 MiB、NVML total=32768 MiB。
記録の NVML free は CUDA free+0.75 MiB。これらを混ぜた差分を payload としない。

M1 は vision dummy shape reserveであり、実画像 forward の peakは未試験。

4. warmup と主モデル出力一致が示している範囲

GPU private graph は4層 × H1..6 ×3 repeats =72 graph computes。
source とログは24 cellsの最終出力 readback が finiteかつゼロだったことを示す。
各cellの3回を終えてから1回 readbackするので、72回すべての中間出力をそれぞれ
保存・照合したという意味ではない。zero inputは実 activation精度試験ではない。

主モデルでは short64 と long1024、それぞれ prefix最終出力 +4T1 の5 rows、
1row129280 F32のbyte列が bankなし/保持で完全一致した。
比較する片側の総スカラー数は1292800。
top2、top1 margin、target logprobも独立に再算出し BANK_COMPARISON と一致。
short64 のT1 4rowsは前回 F-before の correct_F.f32とも完全一致。

全3runを通じて保存された10case×5rows=6464000 F32 valuesは独立にfinite検査。
pilot の残り60T1/caseについては、sourceのfull-vector scanと正常完了記録が
有限性を支持するが、生のF32 vectorは保存されていない。独立再検査済みと
主張できるのは保存済み5rows/caseに限る。

actual prefill ubatchesは raw attemptsから [64] / [1024] と再確認。
prefill時間はshort約5.147秒/5.319秒、long約16.731秒/16.659秒。各1回だけであり、
高速化・劣化・同等性の性能推定に使うには不足する。

5. 20caseの token freeze と next-token 対応

前回の合成corpus hashは維持され、20case/12families、train10/validation5/holdout5
の分割もそのまま。元prompt/reference、rendered prefix、joined text、prefix IDs、
first64 input IDsのhashと相互対応を再確認した。

prefix長187–317、reference継続195–337 tokensで全caseに65 targets以上ある。
assistant boundaryは全case <｜Assistant｜></think> 。tokenizer flags、記録された
thinking_mode=chat、template hashを照合。prefixとreferenceをjoinしてtokenize後、
prefixが厳密なtoken prefixであることを検査するsourceがあり、その成功記録がある。
元APIのtoken-piece response全体は保存されておらず、この監査でモデルtokenizer
を動かして再tokenizeしたわけではない。

API preprocessはsource上 /props、/apply-template、/tokenize だけを使う。
残り15caseのtemplate/tokenizerを凍結したことを、その15caseのrouteを測定したこと
と混同しない。今回のmodel inferenceは下記first5とshort64 controlだけである。

next-tokenのoff-by-oneは見当たらなかった。reference tokenをC0,C1,...とすると:
  prefix最終logit -> C0を評価
  T1 #0にC0を入力 -> 次のC1を評価
  ...
  T1 #63にC63を入力 -> 次のC64を評価
このため64回のT1入力に対して65個のtargetが必要。
raw、PILOT_TOKENS、callerの3者が対応する。
first64のdecoded bytesは元referenceのbyte prefixであることも確認した。

source参照:
  freeze_pilot_tokens.py:24–48 template設定、join prefix検査、first65/64凍結
  pilot-capture/driver.cpp:149–181 再tokenize照合、prefix/continuation/target保存

10. この証拠から次へ引き継げること

・ubatch512やallocator probeを先に必須とする根拠は、今回のfixtureでは解消した。
・元のparallel目標へ戻る前提として、小さいnative bankをU1024で初期化できる
  こと、teacher forcing/route/token境界を固定できることが整った。
・次のactual bank候補を確保するときは、その候補固有のlayer数/reachable Hで
  同じguardを通し、32expert fixtureのadmissionを流用しない。
・35expert案のnative fitとH分布は再現できる。速さの価値は実activationと実時間の
  測定へ委ね、hit率やremaining slotsだけで採用しない。
・validation/holdoutのrouteは未使用。現段階でtrainingに合った配置という位置付け
  を維持できている。
・APIの2tokenずつ表示、実際のparallel overlap、回答品質は今回の評価範囲外。
  それらを今回のbank保持成功やgeneration記録だけで説明しない。

付録: 親の条件付き8層案の独立検算

主監査完了後、親が追加した bank tradeoff script と結果・planを読み、別方式の
標準ライブラリだけの疎なPareto frontier DPを作ってraw first5から再計算した。
親のNumPy DPやrepo scriptは実行・importしていない。

ここでの条件は「native予算480706560 B以内で、元35expert案のtraining inclusion
count4176の90%以上、すなわち3759以上を残す最小active layer数」。同じ個々のhitを
90%残す条件でも、速度・品質の90%を保証する条件でもない。

各層では1expert当たりのnative byteが同一なので、n個選ぶときは頻度上位n個が
aggregate count最大。他の層から何を選ぶかと独立に成立する。この層ごとの
0..n選択肢を37層についてDPし、stageとactive layer数が同じ状態で、少ないbyteで
同等以上のcountを持つ状態に支配された状態だけを除外した。
