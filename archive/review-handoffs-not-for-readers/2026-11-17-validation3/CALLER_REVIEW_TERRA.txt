Finding requiring attention: failure-path answer evidence
caller/driver.cpp:177-183 selects a token, stores it in an in-memory vector, and assembles its event, but if that token requires another decode it calls compute() before writing/flushing the event. If that decode fails, the most recently sampled token and its piece bytes are absent from the JSONL; the complete partial generated_ids array is not saved because answer JSON is written after the loop. Earlier flushed events and the started file remain, and RUN is failed. The normal cap-reached path does write the 1024th event and saves the truncated partial answer. To preserve failure evidence too, journal the selected-token event before decoding, or explicitly save pending token/partial IDs and failure location on exception, with unambiguous event accounting. Do not present failure as a complete response.

Quality and measured intervals
Each quality case runs prefix plus 64 teacher-forced calls; saved row 0 predicts continuation token 0, rows 1-64 predict continuation tokens 1-64; no off-by-one found (145-156). All quality rows are finite checked and saved raw. The timing stage records all 64 T1 calls including the first, start immediately before llama_decode through llama_get_logits_ith output-ready; it omits finite/logit copies inside those intervals. Prefill is separate, and setup, model load, selection, KV clear, JSON and analysis are outside those T1 boundaries. Quality mode does extra finite checks, vector copies and stats snapshots after individual calls, and is not an interchangeable throughput measurement. DESIGN uses four independent F/P/P/F timing processes, with forward/reverse case orders: only two processes per mode on three cases, a small bounded diagnostic rather than general workload performance.
