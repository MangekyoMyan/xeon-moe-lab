CPU / CUDA の算術差: 親エージェントによる解釈
2026-11-12

今回の作業
ユーザー指定の gpt-6.1-terra / max に、要約ではなく、原文・行番号・分岐・ビルド条件を含む調査台帳を作成させた。親は台帳本文を読み、保存済み数値試験を独立して再集計した。
API停止・再起動、モデル読み込み、ビルド、新しい推論ベンチマーク、エンジン設定変更は行っていない。
TERRA_EVIDENCE.txt が証拠台帳、本ファイルはその解釈である。

現時点で確定した違い

1. IQ系では、演算に使う入力の量子化方式そのものが違う。
  対象: IQ2_S / IQ3_XXS / IQ3_S の expert weight。
  CPU: F32入力 -> Q8_K。256要素ごとに1個のFP32スケール。
       絶対最大要素の符号も使い、iscale=-127/max、d=1/iscale。
       nearest_intによる丸めを行う。16要素ごとの整数和bsumsも格納する。
  CUDA T=1 MMVQ: F32入力 -> Q8_1。32要素ごとに1個のFP16スケール。
       d=amax/127、roundf(x/d)。同じ256要素に最大8個のスケールを使う。
       Q8_1には和の欄もあるが、今回の4種のMMVQ dotはscale側だけを読み、和による補正は使用しない。
  これはモデル重みのファイルを書き換える操作ではない。KVキャッシュの型の話でもない。
  expertのgate/upへ入る値と、SwiGLU後にdownへ入る値を、その都度整数内積用に変換する話である。

  解釈: 入力を丸めて保持する値が最初から違い得る。CPUとGPUの最後の加算順だけを揃えても、この差は消えない。
  32要素単位なら、256要素の別の場所にある大きな値にスケールを引っ張られにくい。一方CUDAはスケール自体をFP16に丸める。このコード差だけから、あらゆる入力でCUDAの方が正確とは証明できない。

2. MXFP4では入力の量子化単位が近い。
  CPU: Q8_0、32要素、正のamax/127スケールをFP16格納。
  CUDA: Q8_1、32要素、正のamax/127スケールをFP16格納。
  ただしCPU AVXは127/amaxとの乗算とround-to-nearest、CUDAはx/dとroundfであり、境界値で一致する保証はない。
  CPUのMXFP4最適化は重みのニブルを整数値へ展開し、SSSE3系の整数積和を実施、スケールを掛けてFP32で累積する。入力の補正とスケールを再利用するsidecarは既存Q8_0の算術を維持する設計。
  CUDA MMVQも重みを整数値へ展開し、DP4Aによる整数内積の後にFP32スケールを適用する。この経路をVoltaのネイティブFP4/Tensor Core計算と理解するのは誤り。

3. 入力変換以外にも、算術上の違いがある。
  CPU compact: 128bit整数SIMDの積和 -> FP32の8 lane累積 -> 水平和。今回追加したkernelは-fno-fast-mathと-ffp-contract=offを指定。再利用したCPU objectもIvy Bridge向けの-mno-fmaであり、CPU全objectに同じ追加フラグが付いているとまでは扱わない。
  CUDA MMVQ: 各threadの整数内積とFP32部分和 -> warp間の部分和 -> warp内縮約。CPUと加算の順番は同じではない。
  CUDA IQ2_S/IQ3_XXSには整数の /2、/4 がある。CPUの対応実装は整数和をFP32に変換した後、最終的に1/8や1/4を掛ける。割り切れない中間値では差が生まれ得るが、実モデルのどこで何回起きたかは未測定。
  SwiGLU clampの数式は両者で対応している。CPUとCUDAのexpf、ビルドの高速演算設定、融合・非融合の違いは数値差の候補。実際の差の寄与率を測ったわけではない。
  gate/upの型・形・入力等が条件を満たすと、CUDAはgate/up/SwiGLUを融合できる。中間gate/upバッファが書かれないことと、計算が省略されたことを混同しない。

既存の実測と照合

ここでの参照値は、現在の量子化済みGGUF重みをF32へ展開し、内積をFP64で累積するもの。projection出力はF32に戻し、SwiGLU自体はF32で計算する。量子化前の元モデルとの比較ではない。
NMSE = sum((結果 - 参照)^2) / sum(参照^2)。回答の誤答率ではない。

Layer 4: gate/up = IQ3_XXS、down = IQ2_S。
  seed19: CPU対参照 NMSE 2.16298e-4、全6expertをGPUで計算すると9.02442e-5。
  seed37: CPU対参照 NMSE 2.02039e-4、GPU 9.21584e-5。
  seed83: CPU対参照 NMSE 2.36455e-4、GPU 9.30191e-5。
  この3条件ではGPUの誤差指標がCPUの約39〜46%だった。

Layer 24: gate/up/down = MXFP4。
  同じ3seedでGPU対CPUのNMSEは4.11e-15〜4.42e-15。
  CPU/GPUの参照値に対するNMSEはいずれも約8.1e-5〜8.3e-5で、ほぼ同じ。

今回の解釈

「CPUが正解で、CUDAへ送った分が誤っている」という前提は置けない。少なくとも保存されたIQ系の限定試験ではCUDAの方が上記参照へ近い。
最も先に切り分けるべき差はIQ系の入力量子化方式である。これはコードで確定した差であり、IQ層とMXFP4層で観測された差の大きさとも整合する。ただし、256地点の出力確率差の主因であることを単独実験で証明したわけではない。
モデル全体のhot14比較では、GPU常駐expertの追加と同時に既存GPU層37〜39をCPUへ戻し、CPU compact対象も変更している。計算担当が両方向に変わる比較であり、hot14の全変化を新しい常駐expertだけに帰属できない。
同じ入力トークン列を使っても、各構成で生成される中間値・KV内容・後続routingまで同一になるわけではない。
既存CPU dispatcherのall-miss試験は同じ配置のまま出力が一致した。したがって単にdispatcherを挟むだけで必ず値が変わる、という証拠はない。

次の検証を行うなら

最初に同一のF32入力と同一expertで、入力変換後、gate/up出力、SwiGLU出力、down出力を比較する。IQ3_Sも独立対象へ加える。
その上で量子化単位、scale精度、丸め方、整数除算、非線形関数を一つずつ揃え、どこで差が減るかを測る。
判定基準は既存CPUとのbit一致だけでなく、参照演算への誤差と回答品質を含める。CPUとの完全一致を得るために、より参照に近いCUDA計算を粗くすることを目的にしない。
一般品質の判断には正解付き課題や文章評価が別途必要。現時点では品質が上がったとも下がったとも確定しない。

今回の成果物は調査記録だけであり、通常APIの構成は変更していない。

ライブラリの照合で判明した注意点
親が現在の通常API pid492519の/proc/mapsを読み取り限定で一度確認した。CPUはmx-prepack/release-candidate-a、CUDAはcuda-sort/release-candidate-a、libllamaはsparse-cache/release-v2-aだった。
共通演算ライブラリlibggml-baseはbuild/binではなく、LD_LIBRARY_PATHで先に指定されたgpu-stream-20261103/runtimeが実際にロードされていた。SHA256は2e13b3701059c1529b97b185bdc659d3dc4730e0763ed3bb8eb9cdb9563cc558。台帳Aの元build情報と実行時libraryを区別すること。台帳Fに訂正・ソース追跡を記録した。
このbaseはschedulerを差し替えているが、量子化本体ggml-quants.c.oは元deepseek buildから再利用している。Q8_Kの説明はこの経路も照合したもの。
現在の通常APIの観測であり、過去のhot14プロセスを再起動して確認したわけではない。
