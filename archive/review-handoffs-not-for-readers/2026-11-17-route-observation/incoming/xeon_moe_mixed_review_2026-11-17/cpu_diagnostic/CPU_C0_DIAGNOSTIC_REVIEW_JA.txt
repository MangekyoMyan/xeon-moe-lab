0. 結論と、この成果物の範囲
============================
次の主作業はGPU観測のsource契約・容量確認へ移してよい。CPU absは「mixedの利益あり、C0のcross-library
総時間が事前基準外なので採用保留」のまま残す。本書は、CPU枝へ戻る具体的理由が
できた時の診断仕様であり、追加実機試行の実施命令でも採用gateの変更でもない。

追加CPU観測の第一候補は、read-onlyのprocess contextと、元wall境界の外側に置く
CLOCK_PROCESS_CPUTIME_ID + getrusage(RUSAGE_SELF)である。まずperf群を増やさない。
CPU time / context switch / faultsは「遅延時に何が伴うか」を増やすが、各processが
一つのlibraryしか使わない現設計のlibrary/process交絡を、それだけで因果分離しない。
新しいcounterが無反応でも、Eに固定費用なし／外乱なしとは結論できない。

本担当が行ったのはsource・保存raw/STATUS/maps/guardの読み取り、一次API文書の照合、
offlineの整数割当検査のみ。モデル、既存CPU library、API、GPU、ベンチを動かしていない。
時刻/counterの動作試験も行っていない。新しいharness・launcherの実装もしていない。
重要コードを編集する場合は親担当がこの契約とsourceを照合する。

同梱:
  CPU_DIAGNOSTIC_CONTRACT.json   未実装の機械可読仕様
  SAVED_CONTEXT_AUDIT.json       保存8processのcontextと48source/evidenceのhash

3. C0で残るlibrary差の意味
===========================
E/offはFそのものではない。A/ggml-cpu.c:1791–1799はmode0でもshape/state処理と
追加領域の予約を行う。3194–3197のplanner追加もmode非依存。A/iq-abs.h:39–45では
K5120、inputs1、nth12のabs領域は5120*12+8*12=61,536 B、plannerはさらに63 Bの
alignment余裕を足す。追加領域は既存row map/current_chunk等の後ろにあるので、
この差分だけを根拠に「以前のrow map offsetがずれる」とは言えない。

E/sharedはC0でも1856–1867のinput preparationを実行する。compact lookupは1914–1915。
従ってcache missだけから「sharedの仕事は完全にゼロ」とは言えない。一方、この構造を
今回の+2.74%や+2.99%の主因だと測定なしに断定もしない。workspace量、命令数、code
layout、allocator、NUMA、page state、実行周波数、schedulerは別の変数である。

識別の限界は設計上のものでもある。F/Eはprocess間で切り替わり、process内でF→Eへ
切り替えていない。任意のprocess固定効果を同時に許せばlibrary効果と完全に分けられない。
counterを説明変数に入れた回帰も、原因を自動的に同定しない。library自身がwaitや
faultを変える場合、counterを差し引いて「補正」することは効果の一部を消し得る。

4. まず取得価値がある計時外context
=================================
将来の実機診断では、counterを大量追加する前に以下を記録する。すべてread-only。
現在の通常APIにqueryを追加せず、既存guardの運用契約・制限は維持する。

・process自身の/proc/self/cgroup、/proc/self/mountinfo、PID、kernel release、boot ID、
  scheduler policy/nice、affinity、実threads/TIDs、既存topologyを記録する。
  shell/launcherだけのcgroupをharness自身の値とみなさない。
  warmed workerの/proc/self/task/<tid>/cgroupも一度照合する。thread単位のcgroup配置が
  許される構成を、mainのmembershipだけで全worker同一と仮定しない。
・cgroup v2は、上記から解決したleafと可視ancestorのcpu.max / cpu.statを保存する。
  cpu.stat.local、cpu.max.burst、cpu.pressure等は存在時だけ読む。v1なら対応する
  cpu.cfs_quota_us / cpu.cfs_period_us / cpu.statを存在時だけ読む。未知項目もraw保持。
  namespace/mount rootを考慮し、/sys/fs/cgroupを文字列連結で決め打ちしない。
  見えないancestor・未提供fieldはunknown。leafのmaxだけで無制限と判定しない。
・cpu.statとPSI totalはcase前後に、monotonic read開始/終了とともに取得する。
  group共有・ancestorの値は他process/descendantも含み得る。増加してもharness単独の
  kernel原因とは言えない。counter差分はcaseの診断で、32-call wallだけの値ではない。
  /proc/pressure/cpuはhost範囲として分離。PSI avg10と短いchunkの時間率を同一視しない。
・OMP_WAIT_POLICY / GOMP_SPINCOUNT / KMP_BLOCKTIME等の存在/値、pool.pollとstrict_cpu、
  loaded OpenMP runtimeのpath/hash/versionを記録する。値を今回新規設定しない。
  現launcherはOMP_/GOMP_を除去し固定OMP三項目だけ戻す(173–185)。ggml側の初期化後
  に採るreceiptが望ましい。A/ggml-cpu.c:4194–4205ではOMP_WAIT_POLICY設定はコメント、
  KMP_BLOCKTIMEのdefault設定は実コードなので、launcher前のenvだけでは足りない。
・mapsに加え必要時はnuma_mapsを計時外に取得する。numa_mapsは仮想空間をscanする
  ためper-chunkの安価な観測には入れない。最初の案では全timed loop終了後、Resources
  cleanup前(308–309付近)に一回。これはpost-run配置で、C0実行中の配置証明ではない。
  C0専用の前後配置が不可欠になった場合に限りcase境界へ追加し、その負担を記録する。

CPU bandwidth quotaはthermal throttleとは別の機構である[D4,D5]。quotaが見つかった
場合も、それを解除する、新cgroupへ移す、CPU/NUMA policyを変えることは本提案に含めない。
unknownの場合に既存条件を推測で緩和しない。NUMA page数はremote access数ではなく、
mapsのASLR address差も性能差の原因を証明しない[D8]。

5. 最小per-chunk snapshotの仕様
===============================
全threadsの観測として、CLOCK_PROCESS_CPUTIME_IDとRUSAGE_SELFを用いる[D1,D2]。
RUSAGE_THREAD、CLOCK_THREAD_CPUTIME_IDをmainだけで読む方式では
worker11本を含めた観測にならない。launcher側のRUSAGE_SELFはlauncherの資源であり、
RUSAGE_CHILDRENは終了・wait済み子の集計なのでchunk目的に合わない。

取り方は以下の固定順とする。既存32-call loop内へsyscall、JSON、file I/O、追加barrier、
atomic counter、OpenMP regionを入れない。pre/post用領域はwarmupより前に確保・touchする。

  mode(actual); compute();           // 元の計時外一回。移動・削除しない
  pre.read_begin_mono_ns = monotonic()
  getrusage(RUSAGE_SELF, pre.ru)
  pre.process_cpu_ns = process_cpu_clock()
  pre.read_end_mono_ns = monotonic()
  begin = monotonic()                // 元のwall begin
  32回 compute()                     // 元のloop
  end = monotonic()                  // 元のwall end
  post.read_begin_mono_ns = monotonic()
  post.process_cpu_ns = process_cpu_clock()
  getrusage(RUSAGE_SELF, post.ru)
  post.read_end_mono_ns = monotonic()
  元のneed/tensor_get/memcmp/sample追加

preはrusage→CPU、postはCPU→rusageにしてCPU clockをwallへ近づける。各callは原子的な
共通時刻のsnapshotではなく、process全threadの資源は別API・別時点で読む。従って
counter窓が元wallより広いことを明示する。pre/post read envelopeを保存し、後から
wallと完全同一区間だったように表示しない。CPU clockとrusage CPU timeの厳密一致も
要求しない。rusageのCPU timevalはsec/usecを整数で保存する。

最小counter:
  process CPU nanoseconds
  ru_utime / ru_stime
  ru_nvcsw / ru_nivcsw
  ru_minflt / ru_majflt
各pre/post生値を残し、差分だけにしない。ru_maxrssは高水位なのでchunk RSS差分として
使わない。未維持fieldの0を「そのeventがない」と読まない[D1]。

派生値はwall_ns、cpu_delta_ns、user/system_us、各switch/fault delta、read_duration、
counter窓の余白を別項目で出す。cpu_delta/wallは平均的なprocess CPU占有量の手掛かりで、
1を超えるのは多threadなら自然である。これを12から引いて「scheduler待ち時間」と
する演算や、CPU time増分を「追加命令の時間」とする解釈はしない。spin・stalls・周波数・
unbalanced worker・API窓差が混ざる。全thread集計はどのworkerが遅れたかも示さない。

clock_getresをprocess開始時に保存し、CLOCK_MONOTONICは元のまま用いる。異なるwall clock
へ差し替えない。run/case境界でmonotonic-before → realtime → monotonic-afterの組を
保存すると外部sensorとの対応に幅を付けられる。realtimeのjumpやdaemon timestampの
古さは別に残り、clock pairだけで温度因果が証明できるわけではない[D2]。

6. 観測負担の対照
=================
snapshotをwallの外に置けば直接のsyscall時間はwallから除けるが、直前のcache/TLB状態や
OpenMP spin/sleepへの影響は残る。GNU libgompはwait policy/spin設定によって待ち方が
変わる[D9,D10]。空snapshotを何回か測った費用をwallから引くだけでは、この影響を消せない。

将来C0診断を行う場合の小さい対照候補は、同じ新harness binary内で
  diagnostic_enabled = ((arm + block % 8) & 1)
を事前固定する方式である。各4-arm blockでlogical O/Sそれぞれ1本on・1本offとなる。
同routeのblock+8は元のmode順が反転し、modeに対する位置の偏りも入れ替わる。
64 C0 wall chunksは全保存、うち32にcounter、32はcounter fields=nullと理由を明示する。
SAVED_CONTEXT_AUDIT.jsonでこの組合せだけを整数計算し確認した。collectorは未実装。

これは診断のon/off対照であり、旧screenの追試でもpass探索でもない。比較は
F placebo、E S/O、F対E/O・Sを保ちつつ、diagnostic on/offを別軸に出す。
全wall総和を残し、counterがある半分だけを性能集計として選ばない。counterなしの
chunkを0 counters扱いしない。period/preceding-armからのcarryoverも依然あり、対照が
無差だからobserver effectゼロと断定しない。

全chunkにcounterが必要な将来目的ならfull samplingを事前選択してもよいが、
負担対照を別に設計する必要がある。途中で良い方へ選び替えない。いずれも新harness
buildになるため、元harnessと同一byteの追試ではない。新旧結果を混ぜて旧gateを再採点しない。

8. perf等を先送りする理由と、必要になった場合の条件
==================================================
最小snapshotで説明できないscheduled CPU側の増加が残り、対応を決める必要がある時だけ
次段を検討する。PMUはsampling/callstackではなく少数counting eventから始める。
候補はinstructions / cycles / ref-cycles。未対応eventを勝手に別eventへ替えない。
event nameだけで意味を決めず実CPU/PMU/kernelの仕様を照合する[D3]。

threads作成後にmainへperf_event_open(pid=0,cpu=-1,inherit=1)を一つ開くだけでは、
既存workers全体を覆わない。inheritは新しいchildに対するもの。全workerを測るなら、
全TIDへ適切にattachして寿命を検査する等、明示したcoverage契約が必要になる。
per-thread groupのread窓も同時ではなく、12 groupのreadは最小案より負担が増える。
生counts、event config、exclude_user/kernel等、TID、time_enabled/runningを保存する。
multiplex推定値だけを出さず、coverageが不足した値を未実行eventの0として扱わない。

instructions増は算術以外のspin/dispatchも含む。cycles/instructionsやcycles/ref-cyclesの
変化は仮説を狭め得るが、cache/NUMA/thermal原因の確定ではない。generic cache-missesを
L1 missやremote-memoryアクセスと読み替えない。
whole-process perf statはstartup/mmap/cache packも含み、C0 chunkとの一対一対応を持たない。
外部interval samplingもcaseやchunkの境界をまたぐ。trace/schedstat/per-thread timingは
さらに別の第二段案であり、RUSAGE_THREADをmainに足しただけで代替できない。
権限不足なら未観測として止め、sysctl/cgroup/production設定を変更しない。

9. 採否・保留と、GPUへ先に進む情報価値
=====================================
通常APIは現状維持し、GPU観測のsource契約と容量確認を先に整えることは妥当である。
実captureには診断buildと適切な起動枠が必要であり、稼働APIへ無変更で新計測を接続
できるという意味ではない。route-onlyの別full-model processでも、通常のGPU層37〜39や
KVの確保が加わる点は、実captureの容量・起動計画で別途扱う。
CPU mixed利益は既に記録されており、C0原因を完全同定しても実workloadのhot expert共起、
CPU/GPU completionの重なり、GPUへ逃がせるcritical pathは分からない。一方、そのGPU側
情報は次にどのCPU費用を削る価値があるかも変え得る。このためCPU枝を先に精密化する
機会費用がある。route-only自体をcritical-path割合とみなすことも避ける。

CPU診断を再開する条件:
  ・CPU abs候補の採否が直近の判断を阻み、識別結果で次の実装/観測が変わる。
  ・親が元wall境界・F/O/S階層・新diagnostic schemaを確認し、有限の予定・停止条件を
    実行前に決める。旧8processを理由なく再実行しない。
  ・contextに明白な未把握制約があれば、まずその記録を解釈する。設定変更は別作業。

候補collectorを採る条件:
  ・scopeが全threadsで、counter API失敗・負delta・clock不整合を隠さない。
  ・allocation/touch/file I/O・new barrierが元32-call区間にない。
  ・同一binaryのobserver対照とsnapshot時間を残し、負担が問題規模と区別できないなら
    「低負担で測れた」と言わず診断を保留する。
  ・新source/header/build/library identityと全rawを保存する。新schema/purposeを明示し、
    既存evaluate_screenを自動で適用しない。

再測定で旧遅延が出なかった場合、元結果を取り消さない。「この有限診断では再現せず」
としてCPU保留を維持する。測定を続ければpassが見つかる、という停止規則は置かない。
原因が外部と疑われても、counterで悪い区間を除外して採用基準を満たしたことにはしない。
