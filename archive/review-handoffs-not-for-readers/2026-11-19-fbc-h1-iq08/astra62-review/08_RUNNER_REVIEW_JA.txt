直接数値照合と実 graph の経路

candidate の quality に限り、実 cache table の先頭選択 expert の先頭行から 2 weight block を読む。第 1 Q8_K block は各 32 要素の両半分に -128 を含み、第 2 block は -127 に置換する。400 B×2 の aligned buffer を使い、3 射影×4 丸めを IQ 2 セルで比較する。計 24 回は実 weight 6 例に対する丸め条件の繰返し。d は 1 で、量子化 wrapper の丸め評価や多数の model 入力の品質調査はこの直接照合の対象外。各比較で finite と F32 の全 4 bytes が一致するかを確かめ、最後に元の丸めへ戻す。

直接テストは Fixture の構築中、graph の warmup より前に終わる。quality 用 interposer の累積カウンタでは第 3 warmup の直前直後の差だけを使うため、直接テストの pack/dot 呼出しも前 2 warmup も実 graph 数に入らない。各型の実行行数順は IQ2_S、IQ3_XXS、IQ3_S。cell1 [23040,25600,0]、cell5 [0,27648,30720]、cell6 [0,0,0]。IQ 各 94 blocks、MX 0。MX が先行 IQ の binding を引き継ぐことも、差分計算では問題にならない。計時プロセスは空の LD_PRELOAD であり、snapshot 関数が見つからないことを caller が検査する。

scratch と速度の境界

第 1 warmup より前に同じ graph、12 スレッド、同じ pool に対して ggml_graph_plan の work_size を読む。各 timed fixture.compute() の下では元 backend の ggml_backend_cpu_graph_compute が改めて ggml_graph_plan を呼ぶ。計時項目は graph compute のままで、事前に作った plan を流用する経路に変わっていない。08 の IQ gate/up/down で増える span は 8,000、8,000、21,600 B。全 graph は各 node の最大 scratch と worker の pad を含むため、実際の work_size を比較する。MX の fold が 0 でも caller と planner の共通コードを通る。
