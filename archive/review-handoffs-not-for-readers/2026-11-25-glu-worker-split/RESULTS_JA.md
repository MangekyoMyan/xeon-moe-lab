# DeepSeek第7層のSwiGLUを24コアに分けた実測

**SwiGLU自体は、2つの保存入力の両方で短くなった。gate・up・SwiGLU・downを通した時間では、安定した短縮を判別できなかった。** 第7層の局所比較でいったん区切り、通常APIには現行版を維持した。入力準備の共有を次に試す場合の対照も現行版とする。

2026年11月25日、Xeon E5-2697 v2 ×2、24物理コア、512 GiBのx9ramで計測した。通常モデルはロードしたまま、別プロセスで第7層の選択された実重みと保存入力だけを使った。GPU・API・モデルの再起動は不要だった。[固定した比較条件](DESIGN.json)・[通常APIの照合](LIVE_AFTER.json)

## 何を変え、どう確かめたか

前回の相談資料に書いた「SiLU後のgateに上限10」は誤りだった。稼働CPUの演算は次の順で、候補もまったく同じ式を使った。例えばgate=20、up=1、limit=10での結果は約9.999546である。[訂正したモデル説明](../2026-11-25-specialization-consult/CURRENT_STATE_JA.md)・[対応するCPU演算](../../../vendor/llama.cpp/ggml/src/ggml-cpu/ops.cpp#L3546)

```cpp
const float gate = std::min(src0_p[k], limit);
const float up   = std::clamp(src1_p[k], -limit, limit);
dst_p[k]         = gate / (1.f + expf(-gate)) * up;
```

現行は6人がそれぞれ1 expertの2,304要素を処理する。候補は24人が**6 expertのそれぞれで連続96要素**を処理し、1人576要素となる。F32の2入力clamped SwiGLU、3テンソルとも形状 [2304,6,1,1]、内側が連続、worker数24に限定した。各入力・出力がそれぞれの行strideを使う。出力は各入力と領域が重ならないか、同じ先頭・同じstrideによる完全なin-placeの場合に対応する。部分的に重なる場合は既存の行分担へ戻す。用途は実行時の形状で決まり、このフックだけからテキスト・画像を判定することはできない。新規のpool、backend、コピー、演算間barrierを追加していない。[実装差分](glu-split.patch)

- **実モデル由来の値。** 日本語の同一履歴の異なる位置から保存した第7層の2入力で、双方ともgateとupはIQ2_S、downはIQ3_XXS。元の384 expert形状のまま、読み取り専用のGGUFから該当IDを使い、通常プランと同じcompact/nativeを確認。比較用に展開した量はcell0で119,439,360 B、cell1で99,532,800 B。実行は0–23に固定した物理コア各1スレッド、NUMA 0/1交互配置、THP無効。通常版の約120 GiBの全モデル用compact cacheとはキャッシュ圧力が異なる。[入力の由来とハッシュ](SOURCES.json)・[元の6 IDと各射影](fixture/CELLS.json)
- **数値。** gate・up・SwiGLU各13,824要素、down 30,720要素を各セルで比較した。計**144,384個のF32がすべて有限・全バイト一致**。このうちdownは以前の保存値とも一致した。gate/up/SwiGLUの中間値は今回の現行対照と比較した。計時中は初回、暖機後、各16呼出しのブロック末にdownを保存値と照合した。[ハッシュと比較数](QUALITY.json)
- **実際の分担。** 本物の入力・同じライブラリ・同じGLUテンソルで、計時外に出力をNaNで埋めて1 workerずつ呼び、書かれた位置と値を全件検査した。現行は `2304×6人、0×18人`、候補は `576×24人`、全要素に所有者は1人だった。チームの計算時CPU番号と24個の固有TIDも両版で確認した。診断graphではN=24の各worker・各ノードの時刻を別途保存した。[実入力の分担](QUALITY.json)・[診断生TSVの例](runs/trace-G/cell0-0.tsv)
- **人工境界。** 実際のCPU共有ライブラリを10条件・各版228回の個別worker呼出しで検査。limit前後の隣接F32、±0、大きな正負、独立した行paddingと基点offset、別limit、完全in-place、部分alias、幅・行数・チーム数の不一致、結合入力を含む。各呼出し後に入力・出力と番兵を含む全バッファを期待値とバイト比較した。部分aliasは単一workerのfallback試験であり、任意の重なる並列書込みの安全性を検証したものではない。[検査コード](pointwise.hpp)・[各条件の結果](runs/quality-G/RUN.json)

## 次の相談

Gは比較用に保管する。**次に専用化を試すなら、通常Oを基準に、gateとupで同じQ8入力を一度だけ準備する効果を単独で測る**のが今回の結論。別の候補として、GPUが計算したexpert出力を次のCUDA演算までdevice上に保持する案がある。こちらはGPU側の後続演算が全slotを読める時点までを共通の計測終点にする必要があり、今回のCPUだけの結果から速度を予測できない。
